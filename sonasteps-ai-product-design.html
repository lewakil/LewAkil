What Building SonaSteps Taught Me About AI Product Design

Designing for DHH families has made the boundaries around AI more interesting than the model call itself.

The easiest AI product to build is a text box.

Give the user an input.

Send their message to a model.

Display the response.

You can build something impressive surprisingly quickly.

The harder question comes afterwards:

What exactly did we build?

That question has shaped how I'm thinking about SonaSteps.

SonaSteps is a product for families and caregivers of children who are deaf or hard of hearing. The broader product problem isn't “How do we put a chatbot in the application?”

The more useful question is:

Where can AI reduce the effort required for families to understand and use specialized information?

That distinction matters.

It changes the architecture.

It changes what data the model should see.

It changes where deterministic software belongs.

It changes how retrieval should work.

And it changes where AI should stop.

Some of the architecture I'm describing here is the direction I'm designing toward rather than a claim that every component is already operating in production. That's important because AI prototypes have a tendency to become architecture diagrams before they become systems.

The interesting part is deciding what deserves to become part of the system.

Prototype and planned AI

The current SonaSteps prototype includes activities and guides, family profiles, deterministic suggestions, and caregiver practice history. The AI companion, RAG, model calls, evaluation, and observability discussed here remain planned. Lesson IDs and completion fields in the examples are illustrative; current progress records caregiver practice. Educational material remains draft and subject to review.

See the current SonaSteps case study →

Start with cognitive work, not AI features

A common AI product exercise starts with capabilities:

We could add chat.

We could summarize.

We could use RAG.

We could build an agent.

We could add recommendations.

That's backwards.

I prefer starting with the work the user is already doing.

For a family using specialized educational material, that work might include trying to understand terminology, finding the right lesson, connecting one concept to another, remembering what they've already covered, or figuring out how a lesson applies in ordinary life.

Those are different problems.

And they don't all need the same technical solution.

Sometimes the answer is search.

Sometimes it's better information architecture.

Sometimes it's a deterministic recommendation.

Sometimes AI actually helps.

The useful question isn't:

“Where can we use an LLM?”

It's:

“Where is ambiguity creating work for the user?”

That's where language models become interesting.

The model should not become the application

One of the biggest architectural mistakes I see in AI prototypes is giving the model responsibility for things normal software is better at.

Suppose a family has completed lessons 1, 2, and 4.

The model should not “remember” that.

The application should.

Suppose the user isn't authorized to access another family's information.

The model should not decide that.

The authorization layer should.

Suppose a curriculum defines the next available lesson.

The model doesn't need to invent the curriculum.

The application already has rules.

That leads to a principle I've found useful:

Use AI for ambiguity. Use software for guarantees.

The deterministic application owns things like:

Authentication
Authorization
User state
Family state
Lesson state
Progress
Permissions
Content IDs
Database writes
Business rules
Allowed actions

The AI layer is better suited to things like:

Natural-language understanding
Explanation
Summarization
Retrieval assistance
Question answering
Content discovery
Generating contextual examples
Interpreting user intent

This separation isn't just architectural neatness.

It determines how much you can trust the system.

A family shouldn't need to speak the application's language

Traditional software makes users adapt to its information architecture.

You need to know which menu contains the feature.

You need to know the terminology used by the application.

You need to know whether something is a lesson, resource, activity, module, or setting.

Natural-language interfaces can invert some of that.

Instead of requiring the user to understand the navigation tree, they can say:

“Where can I learn more about this?”

or:

“What does this term mean?”

or:

“Can you explain this lesson more simply?”

The model doesn't have to own the answer.

It can help interpret the question.

That's a subtle but important difference.

For example:

Family question
      ↓
Intent understanding
      ↓
Application search / retrieval
      ↓
Approved SonaSteps content
      ↓
Model explanation
      ↓
Validated response
      ↓
Family

The AI is functioning as an interface between human language and structured application knowledge.

That's much more interesting to me than bolting a generic chatbot onto the corner of the screen.

RAG is useful when the knowledge boundary matters

Retrieval-augmented generation gets discussed so often that “we use RAG” can sound like an AI product strategy by itself.

It isn't.

The useful question is:

Why does this system need retrieval?

For SonaSteps, one potential reason is straightforward.

If a family asks a question about SonaSteps educational content, I don't want the system treating a general-purpose model's training data as the authoritative source.

I want the system to retrieve relevant approved content first.

Conceptually:

Question
   ↓
Retrieve relevant material
   ↓
Build context
   ↓
Model receives:
- user question
- relevant approved material
- response instructions
   ↓
Grounded answer
   ↓
Source references

But even that diagram hides most of the engineering work.

Retrieval raises its own questions.

How is content divided?

What metadata is stored?

Can different content types be searched together?

Should lessons and product-support documentation live in the same retrieval domain?

How do permissions affect retrieval?

What happens when retrieval returns nothing useful?

What happens when it returns something semantically similar but wrong?

How do we evaluate whether the correct content was retrieved?

The model is only one part of the quality problem.

A powerful model with bad context can still produce a confident bad answer.

Retrieval and generation should be evaluated separately

This becomes especially important when debugging.

Suppose the user asks a question and receives a poor answer.

There are at least two major possibilities.

The model may have received the correct information and generated a bad response.

Or the retrieval layer may never have supplied the correct information in the first place.

Those are different failures.

A useful AI evaluation system should therefore be able to ask:

Retrieval: Did we retrieve the right source?

Generation: Given the right source, did the model produce a grounded and useful answer?

If you only evaluate the final response, you can spend hours changing prompts to fix a retrieval problem.

That's one of the broader lessons I take from AI product design: observability has to extend into the AI pipeline.

Personalization doesn't mean sending everything to the model

SonaSteps becomes more interesting when the system can understand some application context.

For example, perhaps the user is currently viewing a particular lesson.

The AI doesn't need every piece of information the application has ever stored about the family.

It may only need:

{
  "currentLesson": "lesson_17",
  "section": "activity_examples",
  "completedLessons": ["lesson_12", "lesson_14"],
  "question": "Can you explain this another way?"
}

That is a better architecture than dumping a complete user record into a prompt because “more context is better.”

Context has cost.

There is token cost.

Latency cost.

Privacy cost.

Relevance cost.

And sometimes quality cost: irrelevant context can make it harder for the model to focus on what actually matters.

Context construction should therefore be an application concern.

The system should deliberately decide:

What does the model need for this request?

Not:

What data can we possibly send it?

Generated examples need a source boundary

One family-facing idea I find interesting is helping translate approved learning material into understandable examples.

Suppose a lesson explains a concept and the parent asks:

“Can you give me another example?”

There are two things happening.

The lesson itself is source material.

The new example is generated material.

The interface should not pretend those are the same thing.

I would rather expose that distinction.

For example:

Based on: Lesson X, section Y

Example: Here's another way this concept might look during a normal family routine…

That design choice helps preserve provenance.

The application can say, in effect:

This is the material we know. This is the explanation or example the AI created from it.

That boundary becomes more important as AI interfaces move beyond simple question answering.

Agents are really about controlled tool access

“Agent” is another word that can hide a lot of architectural detail.

An agent becomes more interesting when the model can do something.

For SonaSteps, imagine the model interprets:

“Show me the lesson we were looking at yesterday.”

The model might determine an intent:

{
  "intent": "find_recent_lesson",
  "requiresTool": true
}

But the model should not query the database directly.

Instead:

Model
  ↓
requests permitted tool
  ↓
Application validates request
  ↓
Authorization check
  ↓
Application queries data
  ↓
Structured result
  ↓
Model / UI

That pattern is much safer and easier to reason about.

The model proposes.

The application decides.

This becomes even more important for write operations.

Reading a lesson is different from changing user data.

Changing user data is different from sending a message.

Sending a message is different from making a high-impact decision.

Autonomy shouldn't be binary.

A principle I like is:

Give AI autonomy proportional to the cost of being wrong.

Human-in-the-loop isn't a weakness

There's sometimes an assumption that the “best” AI product is the one that eliminates the human.

I don't think that's a useful goal.

Sometimes the human is part of the correct architecture.

Especially when the system reaches the edge of its intended knowledge or authority.

SonaSteps can potentially help someone understand educational material.

That does not mean the model should become a medical professional or make individualized clinical decisions.

Those are different responsibilities.

A well-designed system should know when its role changes from:

help explain

to:

this needs appropriate human expertise.

That's not a failure of automation.

That's good product design.

AI safety is partly an architecture problem

It's tempting to treat AI safety as a prompt:

“Do not provide medical advice.”

Prompts matter, but they are only one layer.

Architecture can enforce stronger boundaries.

You can restrict available tools.

You can control retrieved sources.

You can limit the context supplied to the model.

You can validate structured output.

You can require deterministic authorization.

You can prevent arbitrary URL access.

You can separate educational knowledge from product-support knowledge.

You can create escalation paths.

You can log failures.

You can evaluate known edge cases.

The more important the boundary, the less I want it enforced only by asking the model nicely.

AI observability is product infrastructure

Normal applications need observability.

AI applications need it too, but the questions change.

I'd want to know things like:

Which feature invoked the model?
Which model?
What was the latency?
What content was retrieved?
How many sources?
Was a tool called?
Did the tool fail?
Did schema validation fail?
Did retrieval return nothing?
How many tokens were used?
Was the answer escalated?

That doesn't mean indiscriminately logging every piece of family information.

In fact, logging becomes another place where privacy matters.

Operational telemetry and user content should be treated as different things.

You want enough information to understand the system without creating a giant secondary store of sensitive information just because debugging is easier.

Model selection should come after the task

There's another easy trap: starting with the model.

“We're going to use model X.”

Okay.

For what?

Different AI features may have different requirements.

Classification may need speed and structured output more than sophisticated reasoning.

Content discovery may depend more heavily on retrieval quality.

Explanation may require stronger language generation.

A more complex orchestration task may benefit from a different model.

And every model decision has consequences for latency and cost.

I don't think every AI feature automatically deserves the largest available model.

The question should be:

What level of capability does this task require?

Then evaluate models against that task.

A good AI interface doesn't have to look like chat

Chat is powerful because people already know how to use it.

It's also easy for product teams to make chat the entire AI strategy.

But some of the best interactions may be contextual.

Inside a lesson:

Explain this

Give me another example

Ask about this lesson

Inside search:

Describe what you're trying to understand

Inside progress:

Help me understand what we've covered

Then perhaps there is a general “Ask SonaSteps” experience for questions that don't start from a specific page.

AI can be a capability distributed throughout the product rather than a single floating bubble.

The system around the model is the product

The more I work through SonaSteps, the less interesting the raw model call becomes.

Calling an LLM API is easy.

The product work is everything around it:

User
 ↓
Product context
 ↓
Intent
 ↓
Retrieval
 ↓
Permissions
 ↓
Context construction
 ↓
Model
 ↓
Structured output
 ↓
Validation
 ↓
Tools
 ↓
Application state
 ↓
Observability
 ↓
User experience

That's where the engineering decisions live.

It's also where trust lives.

SonaSteps has reinforced something I expect to carry into other AI products:

The model is not the product.

The product is the system that determines when the model should be used, what it is allowed to know, what it is allowed to do, how its output is validated, and what happens when it is wrong.

That's a much harder problem than adding a chat box.

It's also a much more interesting one.
